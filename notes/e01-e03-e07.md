## Lecture E-01: Introduction to APIs

Spring MVC and Spring Boot help us implement the backend. REST and GraphQL describe approaches for making backend functionality available to other software.

## 2. Learning objectives

After these API lectures, you should be able to:

1. Understand the purpose of APIs in web architectures.
2. Differentiate approaches such as REST and GraphQL.
3. Select and apply an appropriate approach for a particular problem.
## Why are APIs needed in web architectures?

The architecture studied previously contains:

- Presentation layer in the browser
- Presentation layer in the web container
- MVC components:
  - View
  - Controller
  - Model
- Business logic layer
- Persistence layer

In the “classic” architecture:

```text
Browser
   ↓
Server-side presentation: View + Controller + Model
   ↓
Business logic
   ↓
Persistence
```

Most work is performed on the server, while the browser mainly displays the result.

▣ **Thin client:** A client that performs relatively little application processing because most presentation processing, business logic and persistence remain on the server.

The lecture gives the following names for this architecture:

- Distributed GUI
- Thin client
- Multi-Page Application or MPA
- “Classic” web application

❗This is only **one possible web architecture**, not the only one.
## 3. Distributed architectures

A web application can divide its layers between client and server in different ways.

### A. Thin client: Distributed GUI

```text
Client: part of presentation
Server: presentation + business logic + persistence
```

The browser mainly displays the server-generated interface.

💡 A traditional Spring MVC application where the server creates HTML pages.

### B. Thin client: Remote GUI

```text
Client: presentation
Server: business logic + persistence
```

The client owns the user interface but calls server-side business logic.

### C. Rich client: Distributed business logic

```text
Client: presentation + some business logic
Server: some business logic + persistence
```

Business logic is divided between the client and server.

💡 The browser validates input and performs calculations, while important operations are still performed on the backend.

### D. Fat client: Remote persistence

```text
Client: presentation + business logic
Server: persistence
```

Most application behaviour runs on the client. The server mainly provides access to stored data.

### E. Fat client: Distributed persistence

```text
Client: presentation + business logic + some persistence
Server: remaining persistence
```

Data-management responsibility is distributed between the client and server.

💡 An application may temporarily store data locally and later communicate with server-side storage.

### Central lesson of the diagrams

When one layer needs to use functionality belonging to another component—particularly across the client/server boundary—it needs a clearly defined interface.

That interface is the **API**.

```text
Component A → API → Component B
```

❗The API is not one particular layer. Depending on the architecture, it may provide access to:

- Server-side presentation functionality
- Business logic
- Persistence functionality
- Other services
## What is an API?

▣ **Application Programming Interface (API):** A logical interface to a software component that hides the internal implementation details and offers selected functionality at a higher level.

An API tells clients **what they may request**, without requiring them to know **how the functionality is implemented internally**.

### Mental model: A restaurant counter

The kitchen is the internal software component. Customers do not enter the kitchen and operate its equipment. They order through the counter using a menu.

```text
Customer → Menu/order counter → Kitchen
Client   → API                → Internal implementation
```

The menu describes what can be ordered. It does not describe every internal cooking step.

→ Result: The kitchen can change internally without forcing customers to learn the new cooking process, provided the menu contract remains stable.

### Purposes of an API

An API:

- Provides a logical view of a component
- Hides implementation details
- Supports modularization
- Integrates separate components or systems
- Promotes code reuse
- Allows multiple applications to use the same functionality

💡 A payment service can expose one payment API. A website, mobile application and internal billing system can all reuse it.
## What can an API specify?

An API can describe:

1. **Supported functions and data types**
   - Which operations can be called?
   - What input is expected?
   - What output is returned?

2. **Available variants or versions**
   - For example, version 1 and version 2 of an API.

3. **Technical and organizational conditions**
   - Authentication
   - Rate limits
   - Usage fees
   - Licences
   - Other restrictions

▣ **Rate limit:** A restriction on how many requests a client may send during a certain period.
## Public and private APIs

▣ **Public API:** An API that is generally available to external developers or applications.

▣ **Private API:** An API available only internally or to selected partners and customers.

💡 A company might use a private inventory API between its own website and warehouse system, while exposing a public product-search API to external developers.
## 4. APIs on the web

The lecture divides important web APIs into two groups.

### Group 1: APIs of the web platform

These APIs define programming interfaces available in browsers and servers.

Examples from WHATWG and W3C standards include:

- DOM API
- WebRTC
- Web Storage
- Fetch API
- Service Workers

💡 JavaScript uses the DOM API to change an HTML element:

```javascript
document.getElementById("message").textContent = "Hello";
```

The browser hides the internal rendering implementation and provides the DOM interface.

### Group 2: Web APIs for services

▣ **Web API for a service:** An interface through which distributed application components or complete systems communicate over the web.

It describes services made available to a client.

Examples from the lecture:

- A browser obtains backend data asynchronously using AJAX.
- A web application outsources functionality to cloud services, such as:
  - Authentication
  - Credit-card payment

Mental flow:

```text
Browser application
       ↓ web request
Service API
       ↓
Backend or cloud service
```

## Lecture E-03: REST APIs with Spring MVC

## Mental model

A normal Spring MVC controller may return the name of a view that should generate HTML.

A REST controller returns **data directly**, usually JSON.

```text
Normal MVC:
Controller → View template → HTML response

REST:
REST controller → Java object → JSON response
```
## Can Spring MVC implement a REST API?

Yes. REST-compliant interfaces can be implemented using Spring MVC.

Spring HATEOAS provides additional support for HATEOAS.

▣ **HATEOAS:** An approach where API responses contain links that help clients discover available related operations.

The lecture does not explain HATEOAS further; it only mentions the supporting Spring project.

❗Most tools needed for REST APIs are the same Spring MVC tools already used for request handling.
## What changes in a REST controller?

In a REST interface, there is no traditional **model-and-view rendering**.

That means the controller does not normally:

1. Put data into a Spring MVC model.
2. Select a view template.
3. Render an HTML page.

Instead, it returns data in the HTTP response.

### `@RestController`

▣ **`@RestController`:** A special stereotype annotation used for REST controllers.

It combines:

```java
@Controller
@ResponseBody
```

▣ **`@ResponseBody`:** Tells Spring to convert the handler method’s return value—for example, into JSON or XML—and write it directly into the HTTP response body.

💡 If a method returns a `Todo` object, Spring can serialize that object as:

```json
{
  "id": 1,
  "title": "Study REST"
}
```
## Which familiar Spring MVC annotations are still used?

REST controllers use the same request-mapping API:

- `@GetMapping`
- `@PostMapping`
- `@PatchMapping`
- Other mapping annotations

They can also use:

- `produces` to restrict the response media type
- `consumes` to restrict the accepted request media type
- `@ResponseStatus` to set the HTTP response status

▣ **Media type:** The format of transmitted data, such as `application/json`.
## Complete REST example from the lecture

```java
/* [...] */

@RestController
@RequestMapping(value = "/api", produces = "application/json")
public class TodoRestController {
  private TodoService service;

  @Autowired
  public TodoRestController(TodoService service) {
    this.service = service;
  }

  @GetMapping
  @ResponseStatus(HttpStatus.OK)
  public Todo[] getAllTodos() {
    return service.getAllTodos();
  }

  @PostMapping(consumes = "application/json")
  @ResponseStatus(HttpStatus.CREATED)
  public Todo createTodo(@RequestBody Todo todo) {
    return service.addTodo(todo);
  }
}
```
## Code explanation

### 1. Declare a REST controller

```java
@RestController
```

This marks the class as a REST controller.

❗The returned Java objects become HTTP response data rather than view names.

### 2. Define the common API URL and response format

```java
@RequestMapping(value = "/api", produces = "application/json")
```

- `value = "/api"`: All handler methods in this controller start at `/api`.
- `produces = "application/json"`: All handler methods return JSON.

### 3. Store the business service

```java
private TodoService service;
```

The controller delegates actual Todo operations to `TodoService`.

### 4. Inject the service

```java
@Autowired
public TodoRestController(TodoService service) {
  this.service = service;
}
```

Spring provides a `TodoService` object through constructor injection.

### 5. Handle a GET request

```java
@GetMapping
@ResponseStatus(HttpStatus.OK)
public Todo[] getAllTodos() {
  return service.getAllTodos();
}
```

A GET request to `/api` executes this method.

- `@GetMapping`: Handles HTTP GET.
- `HttpStatus.OK`: Sends status `200 OK`.
- `Todo[]`: Returns an array of Todo objects.
- Spring converts that array to JSON.

💡 Conceptual response:

```json
[
  {
    "id": 1,
    "title": "Study REST"
  },
  {
    "id": 2,
    "title": "Study GraphQL"
  }
]
```

→ Result: Todo list as JSON + HTTP `200 OK`.

### 6. Handle a POST request

```java
@PostMapping(consumes = "application/json")
@ResponseStatus(HttpStatus.CREATED)
public Todo createTodo(@RequestBody Todo todo) {
  return service.addTodo(todo);
}
```

- `@PostMapping`: Handles HTTP POST.
- `consumes = "application/json"`: The request body must contain JSON.
- `@RequestBody`: Converts the request JSON into a Java `Todo`.
- `service.addTodo(todo)`: Passes the Todo to the business logic.
- The returned Todo is converted back to JSON.
- `HttpStatus.CREATED`: Sends status `201 Created`.

💡 Conceptual request:

```json
{
  "title": "Read API lecture"
}
```

→ Result: Created Todo as JSON + HTTP `201 Created`.

### Complete REST flow

```text
POST /api with JSON
        ↓
@RequestBody converts JSON into Todo
        ↓
TodoRestController
        ↓
TodoService.addTodo(todo)
        ↓
Created Todo
        ↓
Spring converts Todo into JSON
        ↓
201 Created
```

❗The controller manages HTTP communication, while `TodoService` manages the application’s business operation.

## Lecture E-07: GraphQL APIs with Spring Boot

## Mental model

GraphQL starts with a schema that acts like a menu:

```text
GraphQL schema
├── Queries: read data
├── Mutations: change data
└── Types: shape of available data
```

Spring controllers contain resolver methods that implement the operations on this menu.

```text
GraphQL request
      ↓
Schema field
      ↓
Resolver method
      ↓
TodoService
      ↓
GraphQL response
```
## 1. GraphQL ecosystem

GraphQL provides a large ecosystem for different programming languages, including:

- Server-side runtime environments
- Client libraries
- Schema browsers
- IDE plugins
- Other development tools

This lecture focuses on Java implementations.
## What are schema-first and code-first approaches?

### Schema-first

▣ **Schema-first:** The GraphQL schema is written manually first. The corresponding server implementation is created afterward.

```text
Write schema → Implement schema operations
```

Java example from the lecture: `graphql-java`.

❗The schema is the starting contract.

### Code-first

▣ **Code-first:** The implementation code is written or enriched with annotations/configuration first. The GraphQL schema is generated from that code.

```text
Write/enrich code → Generate schema
```

Examples from the lecture:

- `graphql-spqr`: Annotation-based schema definition
- `graphql-jpa`: Generates a schema from existing JPA annotations

| Schema-first | Code-first |
|---|---|
| Schema is written first | Code is written first |
| Implementation follows the schema | Schema is generated from implementation |
| Contract is explicit from the beginning | Schema reflects enriched application code |

The lecture example uses **schema-first**.
## 2. Components used in the example

### `spring-boot-starter-graphql`

It:

- Is based on `graphql-java`
- Provides the runtime environment through a servlet
- Provides an API for implementing the schema

### GraphiQL

▣ **GraphiQL:** A web-based, generic GraphQL client used to develop and test GraphQL requests.

It supports:

- Syntax highlighting
- Code completion
- Validation
- Schema browsing

It is supplied by the Spring Boot GraphQL starter.
## 3. Add the GraphQL runtime

Maven dependency from the lecture:

```xml
[...]
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-graphql</artifactId>
</dependency>
[...]
```

Explanation:

- `groupId`: Identifies the Spring Boot dependency group.
- `artifactId`: Selects the GraphQL starter.
- Spring Boot uses this dependency to configure GraphQL support.

→ Result: The GraphQL API is available at `/graphql` by default.
## 4. Define the GraphQL schema

The schema is stored, for example, in:

```text
src/main/resources/graphql/schema.graphqls
```

Complete schema from the lecture:

```graphql
type Query {
  todos: [Todo!]!
}

type Mutation {
  createTodo(title: String!, text: String): Todo!
}

type Todo {
  id: ID!
  title: String!
  text: String
  comments: [Comment]
}

type Comment {
  id: ID!
  text: String!
}
```

❗By default, Spring Boot expects schema files inside:

```text
src/main/resources/graphql
```

### Schema explanation

#### Query root

```graphql
type Query {
  todos: [Todo!]!
}
```

This declares a read operation named `todos`.

- `[Todo!]`: A list containing Todo objects.
- Inner `!`: An individual Todo in the list cannot be null.
- Outer `!`: The list itself cannot be null.

#### Mutation root

```graphql
type Mutation {
  createTodo(title: String!, text: String): Todo!
}
```

This declares an operation that creates a Todo.

- `title: String!`: `title` is mandatory.
- `text: String`: `text` is optional.
- `Todo!`: The mutation must return a non-null Todo.

#### Todo type

```graphql
type Todo {
  id: ID!
  title: String!
  text: String
  comments: [Comment]
}
```

A client can request the Todo’s:

- Mandatory `id`
- Mandatory `title`
- Optional `text`
- List of comments

#### Comment type

```graphql
type Comment {
  id: ID!
  text: String!
}
```

Every Comment has a mandatory ID and text.
## What is a resolver?

▣ **Resolver:** Code that supplies the value or executes the operation represented by a GraphQL schema field.

Root types such as `Query`, `Mutation` and `Subscription` require root resolvers.

In Spring Boot, resolvers are implemented using controllers, similarly to Spring MVC.

Resolver methods are connected to fields using:

- `@QueryMapping` for queries
- `@MutationMapping` for mutations
- `@SubscriptionMapping` for subscriptions
## 5. Query resolver

Complete code from the lecture:

```java
/* [...] */

@Controller
public class TodoGraphQlController {
  private TodoService todoService;

  @Autowired
  public TodoGraphQlController(TodoService todoService) {
    this.todoService = todoService;
  }

  @QueryMapping("todos")
  public Todo[] getTodos() {
    return todoService.listTodos();
  }
}
```

### Explanation

```java
@Controller
```

Marks the class as a Spring controller containing GraphQL resolver methods.

```java
private TodoService todoService;
```

Stores the business-logic service.

```java
@Autowired
public TodoGraphQlController(TodoService todoService) {
  this.todoService = todoService;
}
```

Injects the service through the constructor.

```java
@QueryMapping("todos")
```

Connects the Java method to this schema field:

```graphql
todos: [Todo!]!
```

```java
public Todo[] getTodos() {
  return todoService.listTodos();
}
```

The method asks the service for the Todo list.

→ Result: When the client executes the `todos` query, Spring calls `getTodos()`.

❗The Java method name is `getTodos`, but the explicit mapping identifies the GraphQL field as `todos`.
## 6. Mutation resolver

Code shown in the lecture:

```java
/* [...] */

@Controller
public class TodoGraphQlController {
  /* [...] */

  @MutationMapping
  public Todo createTodo(@Argument Todo todo) {
    return todoService.createTodo(todo);
  }
}
```

### Explanation

```java
@MutationMapping
```

Maps the method to a mutation. Because no mapping name is provided, the method name `createTodo` is used.

```java
@Argument Todo todo
```

Tells Spring that `todo` should be obtained from a GraphQL argument.

```java
return todoService.createTodo(todo);
```

Delegates Todo creation to the business service.

→ Result: The resolver receives GraphQL input, asks the service to create a Todo and returns the created Todo.

### Important inconsistency in the lecture slides

The schema declares two separate arguments:

```graphql
createTodo(title: String!, text: String): Todo!
```

But the Java resolver expects one argument named `todo`:

```java
createTodo(@Argument Todo todo)
```

These two snippets do **not match exactly**.

With the shown schema, a matching resolver would normally receive `title` and `text` separately:

```java
@MutationMapping
public Todo createTodo(
    @Argument String title,
    @Argument String text
) {
  // create the Todo using title and text
}
```

Alternatively, the schema would need to declare a single input argument named `todo`.

❗For the exam, remember the intended lecture principle:

> `@Argument` maps GraphQL arguments to Java method parameters.

But do not conclude that any arbitrary `Todo` parameter automatically matches separate `title` and `text` arguments.

## Final Connection: REST vs GraphQL Implementation

| Step | REST with Spring MVC | GraphQL with Spring Boot |
|---|---|---|
| Interface definition | URLs, HTTP methods and media types | GraphQL schema |
| Controller type | `@RestController` | `@Controller` |
| Read mapping | `@GetMapping` | `@QueryMapping` |
| Change mapping | `@PostMapping` etc. | `@MutationMapping` |
| Input | `@RequestBody`, URL data, etc. | `@Argument` |
| Output | Java object converted to JSON | GraphQL response based on requested fields |
| Default endpoint | Example uses `/api` | `/graphql` |
| Testing tool mentioned | REST video/example | GraphiQL at `/graphiql` |
| Business logic | `TodoService` | `TodoService` |

## One storyline to remember

A web application can divide presentation, business logic and persistence between different computers. Once components become distributed, they require a defined communication boundary. That boundary is an API.

With REST, Spring MVC exposes operations through HTTP mappings such as GET and POST. `@RestController` returns application data directly as JSON instead of rendering a view.

With GraphQL, the API begins with a schema. Spring resolver methods implement the schema’s query and mutation fields using `@QueryMapping`, `@MutationMapping` and `@Argument`.

In both cases:

```text
Client request
      ↓
API-specific controller/resolver
      ↓
TodoService
      ↓
Result returned through the API
```

❗The API approach changes, but the business logic can remain in the same service layer.
